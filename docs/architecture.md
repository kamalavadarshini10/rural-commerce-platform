# Architecture

## High-Level Stack

| Layer      | Technology                                   |
|------------|-----------------------------------------------|
| Frontend   | React (Vite), JSX, `react-router-dom`, `recharts`, `lucide-react` |
| Backend    | Python, Flask (blueprints), Flask-CORS         |
| Database   | SQLite (file-based, `backend/database/ruralroute.db`) |
| Decision logic | Explainable, rule-based Python (no ML)   |
| Offline    | Browser `localStorage` + store-and-forward sync |
| Evaluation | Python scripts against the same SQLite DB      |

## Backend Structure

```
backend/
  app.py                 - Flask app factory, registers all blueprints
  database/
    db.py                - sqlite3 connection helpers (query_db/insert_db/update_db)
    ruralroute.db         - the SQLite database file (generated by experiments/generate_dataset.py)
  routes/
    auth.py               - POST /api/auth/login
    deliveries.py          - GET /api/deliveries, /<id>, /<id>/instructions, POST /<id>/outcome, GET /failure-reasons
    instructions.py         - POST /api/instructions, GET /api/instructions/customer/<id>, POST /api/instructions/<id>/confirm
    locations.py            - GET /api/locations/<id>/instructions
    confirmations.py        - POST /api/customer-confirmations
    admin.py                - GET /api/admin/analytics, GET /api/admin/repeat-failures
    sync.py                 - POST /api/sync
  services/
    decision_engine.py      - evaluate_instruction_reliability(), get_location_failure_summary()
    delivery_service.py     - apply_delivery_outcome() shared by the outcome route and sync route
  tests/
    test_api.py, conftest.py
```

## Why a Shared `delivery_service.py`?

The single hardest correctness requirement in this system is that an outcome
recorded **offline and synced later** must behave identically to one recorded
**online immediately** — same database writes, same instruction-version
updates, same usage logging. Rather than duplicate that logic between
`routes/deliveries.py` (the live route) and `routes/sync.py` (the replay
route), both call the same `apply_delivery_outcome()` function. This also
made the logic trivially unit-testable independent of Flask's request
context.

## Decision Engine Design

`services/decision_engine.py` implements `evaluate_instruction_reliability`
as an ordered set of rules over the latest `InstructionVersions` row for an
instruction:

1. **LOW** — if the latest version is `failed_delivery_assoc = 1`. This rule
   is checked *first* and unconditionally, so a previous failure can never be
   silently overridden by an older success — the system must never blindly
   recommend instructions after a failure.
2. **HIGH** — if `customer_confirmation_status = 'CONFIRMED'` and the
   confirmation is within the last 30 days.
3. **MEDIUM** — if confirmed, but more than 30 days ago (stale confirmation).
4. **HIGH** — if `successful_delivery_assoc = 1` and that success was within
   the last 30 days.
5. **MEDIUM** — if successful, but more than 30 days ago and never confirmed.
6. **LOW** — default: unconfirmed, no success history, insufficient
   information.

Each branch returns both a `level` and a human-readable `reason` string, so
the same rule that decided the score also explains it — there is no separate
"explanation generator" to keep in sync with the logic.

`get_location_failure_summary()` is a small, separate helper that counts
attempts/failures per location and lists distinct failure reasons; it powers
both the agent's repeat-failure warning banner and the admin repeat-failures
table, so both views are guaranteed to agree.

## Data Model

See `docs/dataset-schema.md` for the full 11-table SQLite schema description
generated during Phase 2. No new tables were added in this implementation
phase — all new functionality (verification tracking, richer confidence
reasoning, etc.) was built on top of the existing schema
(`InstructionUsageLogs.was_verified`, `InstructionVersions.updated_at`, etc.)
per the "do not create unnecessary database tables" rule.

## Frontend Structure

```
frontend/src/
  App.jsx                - routing + login/logout state (stored in localStorage)
  services/api.js         - thin fetch wrapper against the Flask API
  pages/
    Login.jsx              - demo login with one-tap-fill demo accounts
    AgentDashboard.jsx       - delivery list, confidence badge+reason, repeat-failure
                               warning, verify button, outcome recording, offline queue/sync
    CustomerDashboard.jsx    - confirm/update instructions
    AdminDashboard.jsx       - stats, chart, repeat-failure table
```

## Offline Design

The frontend does **not** implement a service worker or complex offline
infrastructure (explicitly out of scope). Instead:

- Delivery/instruction data fetched while online is cached into
  `localStorage`.
- A manual "Simulate Offline" toggle (plus the real `navigator.onLine`
  event) lets the agent's effective online state be tested/demoed reliably
  without needing to physically disconnect a device.
- While offline, outcome submissions are appended to a `syncQueue` array in
  `localStorage` instead of being POSTed immediately.
- When the app detects it is back online, it POSTs the entire queue to
  `/api/sync` in one request and clears whatever synced successfully.
