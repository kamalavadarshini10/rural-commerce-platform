# RuralRoute — Rural Delivery Access Instruction Capture and Reuse System

## Project Overview

Rural delivery locations often don't have standard street addresses. Delivery
agents rediscover the same access information (which gate, which turn, which
landmark) over and over, and locations that have failed before keep failing
for the same reasons because nobody captured what went wrong. RuralRoute is a
college-project prototype that:

1. Captures access instructions from agents and customers.
2. Reuses reliable instructions on future deliveries.
3. Lets customers confirm or correct their own instructions.
4. Warns agents when instructions are unreliable or tied to a past failure.
5. Detects repeat-failure locations for admins.
6. Works with a simple offline/store-and-forward fallback.
7. Provides a baseline-vs-prototype synthetic evaluation.
8. Minimizes agent data entry (dropdowns and one-tap actions over typing).

This is a prototype for a college project — **not** a production logistics
system. See "Known limitations" below.

## Features

- **Explainable confidence engine** (HIGH / MEDIUM / LOW) with a plain-English
  reason for every score — no machine learning, pure rule-based logic.
- **Never blindly trusts instructions after a failure** — a previous failure
  always forces LOW confidence until re-verified.
- **Repeat-failure detection** surfaced both to the agent (warning banner) and
  the admin (dedicated table with attempts, reasons, latest instructions,
  confidence, and reuse status).
- **Customer confirm/update flow** with full instruction version history
  (old versions are preserved, never deleted).
- **Offline mode**: cached data + local outcome queue + real `/api/sync`
  replay, using the *same* backend logic online and offline.
- **GPS-unavailable fallback**: clearly labeled manual/landmark-based mode.
- **Baseline vs prototype synthetic evaluation** with reproducible scripts.

## API Endpoints

The backend exposes the following REST API endpoints:

| Method | Endpoint | Purpose |
|---|---|---|
| POST | `/api/auth/login` | Authenticate a user |
| GET | `/api/deliveries` | Retrieve deliveries |
| GET | `/api/deliveries/<delivery_id>` | Retrieve a specific delivery |
| GET | `/api/deliveries/<delivery_id>/instructions` | Retrieve instructions for a delivery |
| POST | `/api/deliveries/<delivery_id>/outcome` | Record a delivery outcome |
| GET | `/api/deliveries/failure-reasons` | Retrieve available failure reasons |
| POST | `/api/instructions` | Create an access instruction |
| GET | `/api/instructions/customer/<customer_id>` | Retrieve customer instructions |
| POST | `/api/instructions/<instruction_id>/confirm` | Confirm an instruction |
| GET | `/api/admin/analytics` | Retrieve delivery analytics |
| GET | `/api/admin/repeat-failures` | Retrieve repeat-failure information |
| POST | `/api/sync` | Synchronize offline delivery updates |
| GET | `/api/locations/<location_id>/instructions` | Retrieve location instructions |
| POST | `/api/customer-confirmations` | Record customer confirmation |

The `/api/sync` endpoint uses delivery `sync_version` values to detect stale offline updates. Matching versions are synchronized, while older client versions are reported as conflicts and are not applied.

## Database Information

SQLite database at `backend/database/ruralroute.db`, generated by
`experiments/generate_dataset.py` (deterministic, `random.seed(42)`). 11
tables: `Users`, `Customers`, `Locations`, `AccessInstructions`,
`InstructionVersions`, `CustomerConfirmations`, `Deliveries`,
`FailureReasons`, `DeliveryOutcomes`, `InstructionUsageLogs`, `SyncQueue`.
Full schema details in `docs/dataset-schema.md`.

The dataset is intentionally small (7 locations, a handful of historical
deliveries) — enough to demonstrate every required scenario (new location,
past success, past failure, repeat failure, reusable HIGH-confidence
instruction, customer-confirmed instruction, MEDIUM-confidence stale
success, outdated LOW-confidence instruction) without being a large
synthetic dump.

## Database Schema Summary

The SQLite database contains 11 tables:

| Table | Purpose |
|---|---|
| `Users` | Stores application users such as agents and admins |
| `Customers` | Stores customer details |
| `Locations` | Stores rural delivery locations and availability information |
| `AccessInstructions` | Stores active access instructions and confidence scores |
| `InstructionVersions` | Stores instruction history and confirmation status |
| `CustomerConfirmations` | Records customer confirmations or updates |
| `Deliveries` | Stores delivery jobs and their synchronization versions |
| `FailureReasons` | Stores predefined delivery failure reasons |
| `DeliveryOutcomes` | Records delivery attempt results |
| `InstructionUsageLogs` | Records instruction usage during deliveries |
| `SyncQueue` | Stores offline actions waiting for synchronization |

The full schema and synthetic dataset design are documented in `docs/dataset-schema.md`. The dataset is deterministic and can be regenerated using `python generate_dataset.py` from the `experiments/` directory.
## How to Install

Requires Python 3.8+ and Node.js 18+.

```bash
git clone <this repo>  # or unzip the provided archive
cd rural-commerce-platform
```

## How to Run the Backend

```bash
cd backend
python3 -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt

# (Re)build the demo database if you want a fresh, pristine dataset:
cd ../experiments && python generate_dataset.py && cd ../backend

flask run --port=5000
```

The API is served at `http://localhost:5000/api/...`.

## How to Run the Frontend

```bash
cd frontend
npm install
npm run dev
```

Open the printed local URL (typically `http://localhost:5173`). The frontend
expects the backend running at `http://localhost:5000`.

## Demo Flow

1. Log in as **Agent** → view assigned rural deliveries.
2. Open the delivery to location 2 (Red roof house) → see **HIGH** confidence
   with reason "Successfully used on a delivery N day(s) ago."
3. Open the delivery to location 4 (White house, blue gate) → see **LOW**
   confidence with reason referencing the previous failed delivery, plus a
   **repeat-failure warning banner**.
4. Open the delivery to location 7 (Estate bungalow) → see **MEDIUM**
   confidence (old success, never confirmed).
5. Tap "Verify Instructions On-Site", then mark a delivery **SUCCESS** or
   **FAILED** (with a dropdown failure reason + optional note).
6. Tap **"Simulate Offline"**, record another outcome — see the
   `SYNC PENDING` badge — then go back online to watch it auto-sync.
7. Log out, log in as **Customer** → confirm or update the saved
   instructions; updating creates a new version while preserving history.
8. Log out, log in as **Admin** → view delivery statistics, the
   repeat-failure table, and reuse/confirmation counts.
9. Run `cd experiments && python evaluate.py` to see the baseline vs
   prototype comparison.

## Known Limitations

- **Not secure**: login uses plaintext password comparison, no sessions/JWT,
  no HTTPS enforcement — acceptable only for a local classroom demo.
- **No real GPS/mapping hardware integration** — GPS/sensor availability is
  simulated per-location in the seed data, and "GPS unavailable" triggers a
  manual fallback UI rather than talking to real hardware.
- **No service worker / true offline-first architecture** — offline support
  is a `localStorage` queue plus a manual toggle for demo purposes, not a
  production-grade offline-first PWA.
- **Small, hand-designed synthetic dataset** — intentionally small per the
  project brief; not representative of real-world scale or distribution.
- **SQLite + Flask dev server** — fine for a single-user demo, not
  production-load tested.
- **Baseline vs prototype uses the same historical data**, re-summarized two
  ways, rather than two independently run delivery campaigns — see
  `docs/evaluation.md`.
- **Decision engine recency window (30 days)** is a reasonable, simple
  default for a prototype, not a tuned/validated threshold.
